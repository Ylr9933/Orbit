# Agent Infra 开发顺序

建议采用 **“先打通单机最小闭环，再扩展 Agent、任务和集群能力”** 的顺序。各模块可以并行开发，但应围绕同一条可运行链路持续集成。

| 顺序 | 开发内容 | 完成标准 |
| --- | --- | --- |
| **1. 工程基础** | 落地源码目录、依赖管理、安装方式、检查与 CI；明确模块负责人 | 新开发者能按 README 安装并运行检查 |
| **2. 最小接口与测试替身** | 确定 Task 输入输出、Agent 会话、Environment 执行、资源分配、Run/Attempt、事件与产物契约 | 各模块能使用替身独立开发；不一次设计所有未来接口 |
| **3. 单机任务闭环** | Local 资源分配、Docker 环境、简单任务、Run 协调、基础记录 | 提交任务后自动创建容器、执行脚本、保存结果并清理；失败和取消可观察 |
| **4. 宿主机 Agent 接入** | MCP 工具、文件操作、后台作业、增量日志和交互会话 | 宿主机 Agent 能启动容器内训练，断开连接后重连查询、停止作业 |
| **5. 容器内 Agent 与评测** | 接入一个真实 Agent，在任务容器中运行；接入一个原生 benchmark，再用第二种任务验证通用性 | 从任务输入到 Agent 执行、产物归档、原生评测完整跑通 |
| **6. 自动环境准备** | 先支持已有镜像和模板，再增加自然语言生成、参数修改和有限次修复 | 用户描述任务后得到可检查的环境方案，并自动构建和验证 |
| **7. Ray 与跨节点部署** | 节点服务、监控、两节点调度、初始化工具、故障核对 | 跨节点运行正确，资源不会重复分配，节点异常后可诊断和清理 |
| **8. 完善产品体验** | Web、批量实验、查询分析、安装文档和运维工具 | 其他用户可以独立安装、运行任务并定位问题 |

S0 的落实结果见[工程基础计划与验收](s0-engineering-foundation.md)，后续协作见[四人分工](four-person-collaboration.md)。

**这里的顺序是集成顺序，不要求所有人依次等待。** 接口确定后，可以这样并行：

- Environment、Resources、Records 分别开发单机实现。
- Agent 和 Tasks 使用替身开发适配器。
- Run 负责人持续集成最小链路。
- Web 从接口样例开始开发，逐步连接真实后端。
- 集群初始化设计可以提前准备，实机集成放在单机行为稳定之后。

**第一个里程碑应该非常具体：**

> 提交一个简单任务，申请指定 CPU 和内存，在独立 Docker 中运行，产生一个结果文件；平台能查询状态、读取日志、取消执行，容器清理后仍能下载结果。

随后把这个闭环中的“执行脚本”替换为真实 Agent。这样每一步都有可验证成果，接口问题也会较早暴露。

还有两点建议提前落实：**记录、取消和清理从第一条闭环就做；安装文档与自动化检查跟随实现更新。** 这几项会影响所有后续模块，不适合留到最后补。
