# 代码整理、模块衔接检查与下一步计划

状态：本轮整理说明；基于 W 的 `393757b`，位于 `refactor/workflow-integration-audit`。
实现、测试与交付状态见[任务记录](../changes/20260920-integration-audit-r61c4e.md)。本文不代表已经合并或部署。

## 1. 当前结论

当前已经具备**本机、单管理员、小型 CPU 科研工作流**。项目、方案、任务快照、执行、结果记录和界面不是互不相干的样例，已有实际调用链。
本轮重点是修复入口之间的不一致、统一共享逻辑，以及用真实 Docker 验证连接处。

目前适合在独立状态目录中试用小型研究任务。距离日常 GPU 训练、任意 benchmark、多节点和多人在线使用仍有明确缺口。
底层支持某种契约，不等于 CLI、Controller 与 Web 已经开放完整产品流程。

## 2. 两条实际执行链

```text
共同起点：init → Project 工作区 → 研究草稿 → 用户采用指定版本

容器内 Agent：
  Experiment + 材料 → Compilation → 冻结 Task
  → 预检/幂等提交 → Controller → Resources → Environment → Codex
  → Records → 指标引用/Analysis → 用户决策/下一轮

宿主机 Agent：
  项目上下文 → CLI / MCP → Controller → 长期 Docker 环境 → 多轮 Job
  → 日志/归档 → Records → Analysis

Web：读取同一项目和记录；支持编译、预检、提交与取消实验。
     H/E/I 的完整控制仍以 CLI / MCP 为入口。
```

两条路径复用状态、资源准入和记录，但不会强行要求临时科研 Job 先转换成编译 Task。
可选的 E 环境准备产生精确锁引用，供长期环境与编译实验使用。
I 的容器 Planner 消费外置项目状态，只能在事先授权的冻结 Task 集合内迭代；不是无限自主研究。

## 3. 本轮修复与整理

| 问题 | 实际影响 | 本轮处理 |
| --- | --- | --- |
| Web 先启动时，Records 提前创建 Controller 父目录 | 本机复现权限为 `0775`，之后 Controller 的隐私检查拒绝启动 | 统一先创建 `0700` 父目录；旧目录权限有问题时明确报错；新增真实启动顺序回归 |
| state-dir 默认值和路径规则重复 | config-check 曾显示 `./var`，与运行入口默认用户状态目录不同；符号链接规则也不同 | 收拢到 `bootstrap/paths.py`，配置检查与运行入口使用同一默认值 |
| 运行上下文只在一个 CLI 分支补充 | Web、Analysis/Planner 使用的 ResearchService 可能看不到已有运行 | 通过注入运行查询能力统一上下文；只读访问 Controller 库，不创建或升级它 |
| ADMIN 事件过滤在轨迹派生中遗漏 | 事件查询隐藏的内容仍可能进入 trajectory/export | 统一事件/产物可见性；回归覆盖 ADMIN、secret、私有评测及导出 |
| Records 一个文件承担写入、读取、序列化和旧兼容 | 修改边界难以辨认 | 拆分内部 sink、序列化和 legacy writer，对外保留 LocalRecordsStore 与旧导入 |
| 已有内容的目录仍保留占位 | 导航噪音 | 删除 10 个冗余 `.gitkeep`，保留真正空的预留目录 |

没有删除旧 Journal API、历史记录、运行数据或未合并分支。兼容接口有明确用途，不能仅以“仓库内没有调用”为理由删除。
未变更依赖版本、数据库 schema、项目 ID 或冻结 Task 格式。
轨迹过滤修复将 builder 版本升至 `2.0.1`，因此重新导出的 trajectory ID 会变化；旧导出不会被自动重写。

## 4. 当前代码应如何维护

现有模块划分可继续使用，不需要重新搬动整棵目录。新增逻辑优先按职责进入下面的位置。

| 目录/入口 | 负责什么 | 修改时应配套验证 |
| --- | --- | --- |
| `bootstrap/` | 状态根、实例组装、不同模块接线 | 默认/显式配置、多入口一致性、启动顺序 |
| `gateways/cli`、`http`、`mcp` | 参数、协议和有限结果投影 | CLI/HTTP/MCP 相同意图调用相同业务服务 |
| `projects/` | 项目初始化、版本化规划、编译、分析和迭代授权 | 项目/研究版本、材料摘要、幂等和上下文恢复 |
| `tasks/` | Task 清单、可见输入、冻结、导入与评测契约 | 原协议和私有可见性不被改变 |
| `runs/` | 生命周期、控制意图、Job/Planner 协调、清理与查询 | 取消、中断、重复提交及 lease 释放 |
| `agents/` | 提供方命令、认证准备、原生流解释 | 每个 provider 的真实格式和兼容样本 |
| `environments/` | Docker 进程/文件/工作区、环境准备与恢复 | 真实隔离、限额、后台进程和归档 |
| `resources/` | 主机观测、资源请求与准入 | 容量/观测过期/占用冲突；不把观测当授权 |
| `records/` | 原始证据、规范事件、产物、派生轨迹 | 幂等、持久化、可见性、原始数据可追溯 |
| `src/web/` | 项目、实验与结果的交互展示 | 预检失效、丢失响应重试、刷新与错误状态 |

Records 内部现在分为 `local.py`（存储/读取）、`_local_sink.py`（写入）、
`_serialization.py`（内部编码）、`legacy.py`（兼容）和 `visibility.py`（共享读取规则）。
其他模块继续使用已有协议与 store，不依赖私有文件。

仍有一个明确的维护热点：`runs/service.py` 同时协调 phase 执行、流采集、提交冻结、评测和清理，单个方法很长。
下一次对执行内核作功能修改前，应把这些内部阶段逐个提取，保持原调用顺序、finally 清理和 Records 语义。
不应为了缩短文件，一次性改写已经通过隔离/取消验证的状态机。

## 6. 尚不完善的功能

| 方面 | 当前不足 | 对用户的影响 |
| --- | --- | --- |
| 安装与长期使用 | Web 资产单独构建并指定路径；Controller/Web 分开启动；状态目录需统一，旧 catalog 另有 console-dir | 更适合开发者试用，尚不是安装即用的科研工作台 |
| GPU 训练 | 已有 NVIDIA 观测和底层 Docker 参数，但 Controller GPU 准入未开放 | 不能据此承诺可可靠调度实际 GPU 训练 |
| Agent 可替换性 | 有 Codex/Claude Code/DSH 适配器；当前正式提交链路只开放 Codex，其他容器认证/执行链未完整验收 | 更换 provider 不是仅改一个参数就有相同验收范围 |
| 任务工具 | 有工具声明与契约，required ToolBinding 尚未产品化注入 | 有必需额外工具的 Task 会被预检拒绝 |
| 环境准备 | 受限 Python CPU 模板，尚无一般系统包、CUDA/训练镜像模板 | 任意科研依赖无法自动可靠构建 |
| 数据/模型产物 | 缺少外部不可变大数据引用；HTTP 单文件下载上限 16 MiB | 大数据与权重需要人工管理，不能默认通过页面传输 |
| Benchmark | Python 内核支持隔离评测；Controller 入口拒绝带评测 Task，缺原生基准评分等价验收 | 目前不能把任意 benchmark 直接交给 Web 刷榜 |
| 长期实验 | 故障恢复以中断对账和清理为主，无持久等待队列、训练 checkpoint 接续 | 服务崩溃不意味着训练能从原进度继续 |
| Records/Agentic RL | 平台外轨迹靠显式导入；无跨进程 spool、远端备份，CLI 通常缺 token/logprob | 可做事件级分析，不能声称已具备完整 on-policy RL 数据 |
| Web | H 环境/Job、E 构建、I 授权/Planner 生命周期仍需 CLI/MCP；无研究方案在线编辑 | 页面能看结果和提交实验，但尚非全部流程的操作入口 |
| 分布式与协作 | Worker/Ray、多节点加入/鉴权和多用户服务尚未实现 | 单机管理员产品与多人 Git 开发是两个不同层次 |

以上多数是 MVP 边界，不是本轮测试失败。真实科研的方案质量、实验公平性和科学结论还需要领域验证，工程通过不能替代它们。

## 7. 下一步建议：先把日常科研用顺

建议按下列小任务顺序推进，每项都可以独立实现、测试和评审。尚未实施的命令不在此预先命名。

### 第一优先级：可重复安装与一个真实项目

1. **状态与安装诊断**：统一展示实际 state-dir、console-dir、Controller/Web 地址、构建资产、Docker/Agent 可用性；只读且不启动实验。验收：在仓库外运行也能判断自己连的是哪套状态。
2. **启动与恢复说明**：选定常驻路径，提供前台启动和可选服务部署示例、日志位置、备份/恢复步骤。验收：新目录和已有目录均可启动，重启后项目/结果不丢失；启动失败不覆盖已有配置。
3. **真实科研试用**：选一个用户的 CPU 小任务，明确模型和资源预算，经规划、修订、编译、执行、查看结果再迭代一轮。验收：保留真实 Task/Run/Artifact/Analysis 关联，用户无需手改状态库。

### 第二优先级：补齐实际训练所需的入口

4. **GPU 准入**：明确设备允许列表、UUID、独占规则、外部占用处理和失败释放。先完成无 GPU 测试，再在获准设备上验收一张卡的短训练及取消，不直接扩展到多节点。
5. **训练环境模板**：从项目实际使用的一个 CUDA/PyTorch 镜像开始，增加受限模板和 smoke，保存镜像摘要及版本。验收：缺依赖能准确定位，修复受预算约束，失败后不泄漏资源。
6. **大数据与权重**：设计只读外部数据引用及内容/版本标识，增加大产物的安全下载或导出方案。验收：不把数据复制进 Git，不越权读宿主机目录，任务移动后可诊断失效引用。

### 第三优先级：收敛长期维护与界面

7. **拆分 Run 内部阶段**：先提取流采集，再提取 phase 执行/提交收集；每次保持原有取消、私有评测和恢复测试。继续使用一个 Run 协调入口。
8. **Web 长期任务操作**：优先增加已有环境/Job 的日志与停止、环境锁和构建失败信息；复用现有 Controller 接口。验收：刷新恢复，不把关闭网页等同停止训练。
9. **跨入口契约回归**：为新增字段维护一套请求/响应样例，减少 Python/TypeScript 手工漂移；继续保留真实 Web-first 集成与浏览器测试。

ToolBinding、其他 Agent 的完整提交链、原生 benchmark 和 Ray/多节点应各自独立立项。
若近期主要做 benchmark，可把“原生评测接入与等价验收”提前；若主要做科研，应先完成上面的真实项目和 GPU/数据入口。
