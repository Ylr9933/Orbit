# 四人协作分工与具体任务

状态：S0 之后的开发分工方案，尚未指定实际成员。下文是后续要开发的内容，不代表已经实现。工程起点见[S0 计划与验收](s0-engineering-foundation.md)，总体阶段见[开发顺序](development-sequence.md)。

## 1. 按内部相关性分成四组

每个人尽量负责一条连贯的工作链：安排运行、提供执行能力、解决并评价任务、保存并展示信息。相比上一版，把 MCP 和环境工具放在一起，把 Web 和 HTTP/CLI 放在一起，把任务解析与评测留在同一组；Records 归入数据查询与展示这一组。

| 角色 | 工作主题 | 负责范围 | 主要源码位置 |
| --- | --- | --- | --- |
| A | 运行协调与调度 | Run、Resources、Worker、组装与集成 | `runs/`、`resources/`、`gateways/worker/`、`bootstrap/` |
| B | 环境与执行工具 | Environment、文件/命令/作业、工具、MCP | `environments/`、`gateways/mcp/` |
| C | Agent、任务与评测 | Agent 适配、Tasks、原生评测与汇总 | `agents/`、`tasks/` |
| D | 记录与使用入口 | Records、HTTP/CLI、Web | `records/`、`gateways/http/`、`gateways/cli/`、`src/web/` |

表中 Python 路径均相对于 `src/agent_infra/`。这是人员责任划分，模块仍按[架构设计](../architecture/agent-environment-modules.md)保持独立。例如 C 同时负责 Agent 和 Tasks，也不能把包含隐藏答案的完整任务对象直接交给 Agent。

四人的工作量不要求每个阶段完全相同。A 先做 Local，后做 Ray；B 先做容器与命令，再做交互工具；C 先做任务样例和 Agent 替身，再接真实 Agent；D 先做记录和最小 API，后做 Web。每个人都负责自己模块的测试、示例和必要文档。

## 2. A：运行协调与调度

**负责把一次请求安排成完整的执行过程，并知道它进行到哪一步。**

| 部分 | 具体要做的事情 |
| --- | --- |
| 创建运行 | 接收任务、Agent 选择和运行参数；创建 Run/Attempt 标识，关联任务版本、环境、资源和记录 |
| 协调流程 | 调用 C 解析任务，申请资源，调用 B 准备环境，再启动 Agent 或脚本；执行结束后安排归档、评测和清理 |
| 生命周期 | 管理等待、准备、运行、结束等状态；处理失败、取消和超时；按任务协议执行预算与重试规则 |
| 资源管理 | 发现本项目可用的 CPU、内存、GPU；判断请求能否满足，选择节点，维护占用和租约；先本地后 Ray |
| Worker | 接收派发请求，调用 Run 的节点执行逻辑，回报心跳、进度和清理结果；不另写一套运行状态机 |
| 组装与集成 | 在 bootstrap 选择并注入具体后端；把四人的接口接成同一条链路，维护主要集成测试和公共工程入口 |

**交接边界：** 向 B 提供任务环境要求及实际资源分配；向 C 提供运行上下文和受限环境访问能力；将状态变更交给 D 持久化。资源只有在 B 确认进程和容器清理完成后才释放，节点失联时不能直接记为空闲。

**先做什么、如何验收：** S1 用各模块替身验证成功、失败和取消流程；S2 接上 Local、Docker 与持久记录。一个简单任务能从提交走到结果归档和确认清理，失败时能说明停在哪一步。Ray 和两节点故障处理留到 S3。

资源调度与 Run 虽然由同一人维护，Resources 后端仍通过注入的执行入口派发，不反向导入 Run 的具体实现。

## 3. B：环境与执行工具

**负责让任务拥有可用、隔离、可控制的执行环境。**

| 部分 | 具体要做的事情 |
| --- | --- |
| 环境准备 | 根据任务要求使用镜像或模板；创建工作区和容器，准备依赖、挂载材料；落实 A 分配的 CPU、内存和 GPU 限制 |
| 材料隔离 | 按 C 声明、A 传入的可见性要求准备材料；区分 Agent 工作区与评测私有材料，限制文件操作范围 |
| 文件操作 | 提供读取、写入、列目录及输入输出传递能力；处理路径不存在、无权限和越出工作区等情况 |
| 命令和作业 | 执行短命令，启动长时间训练作业；提供作业标识、状态、退出码、增量日志、超时和停止能力 |
| 会话与工具 | 按需要提供持续终端会话及获准工具；明确工具参数、返回结果、错误和权限范围 |
| MCP 入口 | 把运行申请、环境绑定、文件/命令/作业操作转换成 Agent 可调用的工具；运行管理调用 A，执行操作调用绑定环境的受限接口 |
| 收集与清理 | 收集 stdout/stderr 和输出文件，交给 D 的归档接口；停止任务进程、销毁容器和临时目录，向 A 返回实际清理结果 |

**交接边界：** 接收 A 已经分配好的资源；向 C 提供执行能力和工具说明；把执行事件、日志与产物交给 D。B 不决定用哪个 Agent，也不计算 benchmark 分数。

**先做什么、如何验收：** 先在独立 Docker 中执行一个脚本、读写文件并收集结果；再增加长作业查询、增量日志、取消和 MCP。外部 Agent 能启动、查看和停止容器里的作业，环境销毁后已归档结果仍在。

自然语言建环境放在后续任务中：B 提供模板、构建和验证能力，方案生成与用户修改参数的流程由 A/B/C 协作接入，不能让 Environment 反向依赖 Agent 实现。

## 4. C：Agent、任务与评测

**负责理解任务如何交给 Agent，以及结果应该按什么规则评价。** Agent 适配留在 `agents/`；同一 benchmark 的任务解析、评测和汇总放在 `tasks/` 下，公开接口分别维护。

### Agent：接入执行任务的 Agent

- 接入一个真实 Agent 后端，说明如何启动、传入任务、获取输出，以及它支持哪些能力；不要求所有 Agent 使用同一种决策循环。
- 管理会话的关联、输入、状态和取消；不支持恢复或交互的后端要明确声明。
- 支持宿主机已有 Agent 和容器内托管 Agent 两种接入方式。平台托管进程由 B 的执行能力管理，运行时机由 A 协调；宿主机已有 CLI 默认只关联会话，不接管用户的整个 Agent 进程。
- 解释 Agent 原生轨迹，提取能识别的消息和工具调用，并把原始轨迹引用交给 D；说明哪些内部行为无法采集。

### Tasks：说明“这是什么任务、需要什么、应该交付什么”

- **任务索引：** 登记任务 ID、来源、版本和原始材料位置，让平台能列出和选择任务；保留 benchmark 原有目录结构。
- **任务解析：** 读取任务说明、输入数据引用、初始文件及已有配置，转换成平台可理解的任务描述。
- **输入可见性：** 区分给 Agent 的任务说明/公开数据与仅供评测的答案、标签等材料；生成单独的 Agent 可见视图。
- **执行要求：** 声明镜像或依赖、需要的工具、资源需求、超时和预算等；将声明交给 A，由 A/B 分配资源并准备环境。
- **输出约定：** 说明任务应产生什么，例如预测文件、修改后的代码、模型文件或报告，以及它们的格式和位置。
- **任务样例：** 先准备两个原始结构不同的小样例，验证解析可重复、缺失材料有明确报错、隐藏材料不会进入可见视图。

Tasks 不需要自己下载并改写所有 benchmark 数据，也不负责创建 Docker。大型材料使用可追溯引用，测试样例只保留小而必要的文件。

### 评测：说明“交付结果是否符合任务要求、得分如何计算”

- **接入原生评分器：** 明确评分命令、依赖、输入文件和所需私有材料，尽量复用 benchmark 自己的评分方式。
- **准备评测输入：** 根据任务版本和本次冻结的产物找到要评分的文件；缺少必要输出时给出明确结果，不静默补造结果。
- **执行评测：** 向 A 提供评测要求，使用 A/B 准备好的资源与受限执行能力调用评分器；不自行选择集群节点。
- **解释结果：** 提取指标、分数及原始报告引用；区分有效零分、执行失败、评分器失败和无法评测。
- **遵守原协议：** 保留预算、重试、结果选取和汇总方式；由 A 执行运行控制，C 不在评分器里偷偷启动额外重试。
- **验证评分：** 用已知产物验证预期分数与失败行为；允许对已归档产物独立评测，无需重新运行 Agent。随机评分遵循原协议的重复次数和容差。

**交接边界：** 向 A 提供任务描述、可见输入、环境要求、输出约定和评测方案；从 B 获得受限执行能力；通过 D 读取归档产物并保存评测结果。隐藏材料不能经 Agent 轨迹或工具返回泄露。

**先做什么、如何验收：** S1 先完成两种任务样例的解析、可见性测试和 Agent 契约/替身。S2 接入一个真实 Agent、一个原生评分器，再用第二种任务验证通用性。新增任务主要改自己的适配目录，A 不需要增加 benchmark 专用评分分支。

## 5. D：记录与使用入口

**负责把运行信息可靠保存下来，并让用户能提交请求、查询和理解结果。**

| 部分 | 具体要做的事情 |
| --- | --- |
| 元数据 | 保存任务/Agent/环境版本引用、Run/Attempt 关联、配置快照、状态和评测结果；状态由所属业务模块决定，Records 负责保存 |
| 事件与日志 | 接收 A/B/C 产生的事件，支持追加、去重和增量读取；能区分来源与所属 Attempt，不把墙钟时间当成严格因果顺序 |
| 原始轨迹 | 保存可获取的原生轨迹及索引，同时保留统一事件视图；工具参数、结果、stdout/stderr 按实际采集范围保存，较大内容使用产物引用 |
| 产物归档 | 把结果文件保存到独立于任务容器的存储，提供稳定引用、查询与读取；处理文件缺失和归档失败，避免记录成功但文件已经丢失 |
| HTTP/CLI | 提供提交、查询、取消和结果读取入口；校验请求及访问范围，把操作交给 A 等业务公开接口，把查询交给对应查询接口 |
| Web | 逐步实现资源、运行详情、轨迹、评测结果和获准交互页面；通过 HTTP/事件接口工作，刷新后能重新读取持久记录 |

**交接边界：** A/B/C 明确产生哪些事件、何时产生产物；D 提供统一的写入、归档和查询接口。Agent 原生格式由 C 解释，执行日志由 B 采集，D 不猜测没有收到的行为，也不把缺失轨迹展示为完整轨迹。输出可能含凭据时，各方共同确定脱敏和访问范围。

**先做什么、如何验收：** S1 定好最小记录契约、样例和替身；S2 先实现持久记录、产物和最小 HTTP/CLI，再逐步接 Web。任务容器删除或平台进程重启后，仍能查询已归档状态、日志、结果和评分。

Records 不反向导入 HTTP/Web 或业务状态机；Web 不直接访问数据库。D 负责入口与展示，不在页面或 CLI 中复制 A 的运行协调逻辑。

## 6. 用一个任务串起来看

例如：**“读取公开训练数据，训练一个模型，输出预测文件，并按任务协议评分。”** 下面只是职责示例，不是当前可运行功能。

1. **D** 提供提交入口；**A** 创建 Run，并请 **C 的 Tasks** 解析任务材料、执行要求和输出约定。
2. **A 的 Resources** 分配资源；**B** 按要求准备容器与工作区，仅放入获准材料。
3. **A** 调用 **C 的 Agent 适配器** 启动或关联 Agent；Agent 通过 **B** 的执行接口/MCP 操作环境，受支持的原生工具路径由适配器声明。
4. **B/C** 产生执行事件和轨迹，**D** 持续保存；执行结束后 **B/D** 配合冻结并归档预测文件。
5. **A** 安排评测，**C 的评测器** 在获准环境中读取预测文件和评测材料，返回分数；**D** 保存并展示结果。
6. **A** 协调 **B** 清理任务及评测环境，确认实际清理结果后核销资源；清理失败单独记录，不覆盖已经得到的分数。

## 7. 开工顺序与协作约定

**先共同完成 S1 的最小接口，再并行实现。** 接口提供方写协议、成功/失败样例和测试替身，直接调用方一起评审。公开契约放所属模块的 `api.py` 或 `api/`；共享标识与引用放 `contracts/`；替身放 `tests/fakes/<module>/`，不作为生产失败回退。S1 同步补齐公开/内部导入检查及必要的 schema 一致性检查。

| 阶段 | 四人共同交付的结果 |
| --- | --- |
| S1 | 最小契约、共享替身、两种任务样例；各模块能独立验证，A 能用替身串起协调流程 |
| S2 第一步 | A/B/D 打通 Local + Docker + 简单脚本 + 持久记录；C 并行做任务和 Agent 适配，不让真实 Agent 阻塞第一条闭环 |
| S2 后续 | 接入 C 的真实 Agent 与原生评测，验证宿主机与容器内两种模式，补齐取消、超时和清理 |
| S3/S4 | A 扩展 Ray 与故障协调，B 完善节点执行和环境准备，C 扩展任务/Agent 兼容性，D 完善 Web、查询与批量结果展示 |

公共工程入口、`bootstrap/` 和主集成测试由 A 牵头；共享类型由提供方与消费者共同确认；依赖和锁文件由引入依赖的成员同步维护。HTTP 与 MCP 使用一致的访问范围约定，由 D/B 共同对齐。责任人是维护和评审的联系人，不要求所有相关代码只能由他修改。

每个任务使用独立分支，并发 Agent 使用独立 worktree，各自配置状态目录、端口和实际执行资源。显著任务维护 `docs/changes/<task-id>.md`；只在项目能力或阶段变化时更新总进度。详细 Git 和检查流程沿用[CONTRIBUTING](../../CONTRIBUTING.md)与[AGENTS.md](../../AGENTS.md)。

交付时至少说明：改了什么、依赖哪些接口、验证如何运行、哪些只是替身结果、真实环境验证覆盖哪里、是否已经合并。接口改变时同步消费者和文档，合并要满足相关评审与检查。实际成员确定后再将角色映射为真实 CODEOWNERS 账号；目前临时维护者仍为 @XuehaiWang。
