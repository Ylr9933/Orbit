# S0 之后的四人协作分工

状态：S0 工程实现已完成后的协作方案；A/B/C/D 是角色，尚未指定实际成员。人或 Agent 均可承担角色，合并权限仍遵守仓库规则。实现基线见[S0 计划与验收](s0-engineering-foundation.md)，总顺序见[开发顺序](development-sequence.md)。

## 1. 推荐分工

四人分别负责“运行协调、执行基础、Agent 接入、任务与记录”。模块归属保持独立，一个人负责多个模块也不能跨过公开接口直接访问内部实现。

| 角色 | 主要负责范围 | 首批交付 | 主要协作者 |
| --- | --- | --- | --- |
| A：运行协调与集成 | `runs/`、`bootstrap/`、HTTP/CLI 网关；牵头 CI 与公共契约集成 | Run/Attempt 最小契约、使用替身的协调链、统一错误/取消处理、第一条集成用例 | B 的环境/资源、C 的 Agent、D 的任务/记录 |
| B：环境与资源 | `environments/`、`resources/`、Worker 协议适配；对应部署与运维 | 环境管理/访问契约、资源租约、Local 后端，再到 Docker 文件/命令/作业/清理 | A 协调与派发；C 执行访问；D 评测执行与产物 |
| C：Agent 与用户入口 | `agents/`、MCP 网关；后续 `src/web/` | Agent 能力/会话契约及替身，再接一个真实 Agent 和宿主机 MCP 路径 | B 的受限执行接口；A 的运行 API；D 的轨迹归档 |
| D：任务、评测与记录 | `tasks/`、`records/`、任务样例与固定测试材料 | 两种原生结构任务、可见性投影、原生评测协议、事件/产物契约及记录替身 | A 的 Run/Attempt 关联；B 输出收集；C 轨迹来源 |

每人同时维护本模块的测试、示例和文档。Worker 接收协议归 B，节点上的运行协调逻辑仍属于 A 的 `runs/`，不能出现第二套状态机。MCP 协议转换归 C，环境生命周期仍由 A 协调、B 实现。

分工按阶段调整负载：B 在 S2 先做单机，不同时实现 Ray；D 先完成任务解析和记录最小接口，再接完整评测；C 先完成 Agent/MCP，Web 的业务页面随后基于稳定 HTTP 契约开发。A 持续做集成，不独自补完所有落后的模块。Web 尚未开始时不影响 S2 后端验收。

## 2. S1 先交付共同开发依据

当前 S0 只有工程包边界，还不能凭空并行实现完整业务。第一轮共同收敛以下连接点，接口提供方执笔，直接调用方共同评审。

| 接口或规则 | 执笔 | 共同评审 | 先约定的内容 |
| --- | --- | --- | --- |
| Run/Attempt、运行控制与查询 | A | B/C/D | 状态归属、关联标识、成功/失败/取消、完成条件 |
| EnvironmentControl / EnvironmentAccess | B | A/C/D | 准备与销毁权限、文件/命令/作业、超时、输出引用、实际清理结果 |
| 资源分配与派发 | B | A | CPU/内存/GPU 表达、租约、派发请求、等待取消、确认释放 |
| Agent 能力与会话 | C | A/B | 输入/输出、支持的控制动作、运行位置、原生轨迹覆盖 |
| 任务可见视图与评测 | D | A/B/C | 私有材料隔离、环境要求、输出约定、预算、评分/汇总 |
| 事件与产物 | D | A/B/C | 来源、Run/Attempt 关联、去重、原始轨迹引用、读取与归档 |
| 少量共享类型、HTTP schema | A 协调 | 对应提供方和消费者 | 模块类型的唯一来源、序列化、错误表达及未来生成链路 |

公开契约留在所属模块的 `api.py` 或 `api/`；共享目录只放确实跨模块复用的标识、引用等类型。A 负责集成协调，不拥有随意修改所有接口的权限。公共文件出现并行修改时，由本任务指定一位编辑者，其他人提供评审意见，避免同时写同一文件。

每个最小接口交付应包含：类型/协议、最小成功样例、至少一个关键错误或取消样例、可独立使用的明确测试替身、契约测试，以及生产者和消费者的约定。替身集中在 `tests/fakes/<module>/`，由提供方维护；不放到生产代码中作为失败回退。

S1 的完成条件包括：两种结构任务能确定性解析并正确隔离可见输入；各方共享契约与替身可独立验证；A 用同一组契约打通模拟协调测试。涉及对外 schema 时一起交付生成/一致性检查，不提前手写第二份 Web 类型。补上公开/内部导入检查，不只依赖 S0 的方向检查。

## 3. 四人如何依次集成

| 批次 | A | B | C | D | 集成条件 |
| --- | --- | --- | --- | --- | --- |
| S1 契约基线 | Run/Attempt 与集成测试框架 | 环境/资源契约和替身 | Agent 契约和替身 | 任务/记录契约、替身、两种任务材料 | 先合并相容的接口与样例，再扩展真实实现 |
| S2 最小脚本闭环 | 提交→准备→执行→归档→清理 | Local + Docker + 文件/命令/取消 | 用已约定环境替身开发 Agent 适配 | 简单任务与持久事件/产物读取 | 真容器运行脚本；退出/失败/取消可观察，清理后结果仍可读取 |
| S2 Agent 与评测 | 复用同一协调链接 Agent/评测 | 后台作业、日志、会话与受限访问 | 一个真实后端、宿主机 MCP、容器内运行 | 原生评测和第二种任务兼容性 | 两种运行模式各有真实证据；无 benchmark 专用 Run 分支 |
| S3/S4 扩展 | 节点故障协调与批量运行 | Ray、节点初始化和资源恢复 | Web 业务页面、交互恢复 | 查询/轨迹/评测汇总与回归 | 两节点与产品流程按对应阶段分别验收 |

第一条真实闭环使用简单脚本，因而 B/D/A 集成不用等待真实 Agent。C 可以并行验证适配器，但不能在假环境测试通过后宣称真实 CLI 已接通。自动环境准备先做模板再做自然语言方案，按后续单独任务安排，不挤入 S1。

接口改变时，先提交契约、样例与消费者迁移说明；尽可能在一个可审查 PR 中同步生产者和消费者。PR 保持小而可运行，不能先合入破坏其他模块的签名再等待别人修复。依赖中的 PR 可以设计和编写，但完成主线验证前不记为已集成能力。

## 4. 日常协作与共享文件

每位成员从同一已合并基线创建独立任务分支。并发 Agent 使用仓库旁的独立 worktree，人使用各自 clone；每个工作区执行 `make setup`，并分配独立状态目录和端口。具体命令见[CONTRIBUTING](../../CONTRIBUTING.md)。CPU/GPU 和 Docker 资源另外登记，目录隔离不能代替资源分配。

每个显著任务沿用一个 `docs/changes/<task-id>.md`，交接必须包含目标、接口依赖、已完成内容、验证证据和下一步。项目总进度仅在能力或阶段变化时更新，不能每人追加一段会话日志。合并顺序由 A 协调，实际发布/合并仍须满足用户授权、相关评审与检查。

| 共享区域 | 协作方法 |
| --- | --- |
| `contracts/`、`schemas/` | A 协调；类型提供方和消费者共同审查，生成文件从源再生成 |
| `bootstrap/` | A 组装，各模块提供构造配置；业务模块不反向导入它 |
| 依赖清单与锁文件 | 引入依赖的成员负责；提前说明用途，冲突后按统一清单重新生成 |
| CI、Makefile、根规则 | A 维护，影响其他模块的检查变更由受影响成员评审，不绕过失败检查 |
| `docs/project-status.md` | 交付能力的任务提出精简更新；合并时按最新 main 语义协调 |
| `tests/fakes/` 与跨模块测试 | 提供方维护各自替身；A 维护主集成链，避免各自复制一套假协议 |

实际成员确定后，将角色映射成真实 GitHub 账号并更新 CODEOWNERS；当前仅配置 @XuehaiWang 作为临时维护者，不写不存在的 A/B/C/D 账号。人审或 Agent 辅助评审都应指出实际检查证据，Agent 的自述不能代替 GitHub 必需检查或独立评审。

## 5. 每个任务的交付标准

提交前满足仓库规则和相关 `make check` / `make test` / `make build`。更改业务接口需同步消费者、样例、测试和文档；新增真实后端需额外保留对应环境下的执行证据。明确失败、取消、清理和资源释放的责任，不能把“已发出销毁请求”当成“资源已释放”。

每次交接让下一位成员能回答：依赖哪个接口版本、如何独立验证、哪些输出来自替身、哪些已经真实运行、还有什么阻塞，以及变更是否已经进入 main。只有这些信息明确，按模块分工才具备可持续协作的基础。
